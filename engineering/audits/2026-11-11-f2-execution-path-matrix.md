## Bypasses discovered/ruled out (this segment)
- **Discovered & mitigated:** `retry` and `recover` previously executed retry_safe/replay_safe capabilities without re-running `Authorizer`/approval validation at re-execution boundary (could have allowed consequential actions to proceed without fresh valid approval if such capability were configured retry/replay-safe). **Fixed** in `aj/orchestrator.py` with blocker + authorization checks and refusal audit/evidence. **VERIFIED** by F2 tests (no side-effect action executed on denial).
- **Ruled out (tested):** unauthorized side-effecting handle path does not execute; invalid/mismatched approval cannot authorize; forbidden capability cannot execute with approval token. **VERIFIED**.
- **Remaining:** low-level `actions.run` direct calls are not an authorization boundary (internal API concern); stale-policy revalidation for already-authorized consequential AUTHORIZED tasks on resume (single-use approval consumed) **VERIFICATION REQUIRED** by design review; adapter/CLI/background edge paths and exhaustive calling-path coverage **VERIFICATION REQUIRED**. `calling.py` performs explicit `Authorizer.authorize` in `confirm_and_dial` for `helix.place_call` (**PARTIAL/VERIFIED by implementation + existing calling tests, not exhaustively re-run this segment**).

## Durable authorization context / stale-policy protection (2026-11-11 continuation c)

- **Implementation (VERIFIED by code/tests):** `TaskRecord.authorization_context` persists authorization evidence (capability_id, version, risk_level, forbidden, approval_required, payload_fingerprint, outcome, source) when tasks become AUTHORIZED (handle and scheduler/resume promotions). On AUTHORIZED resume continuation, `Aj` revalidates against current spec/payload and refuses execution when context is missing/malformed or materially changed (capability/version/risk/forbidden/approval-stricter/payload fingerprint or capability no longer safely executable).
- **Fail-closed behavior:** consequential/approval-bound stale continuations are moved to `RECOVERY_REQUIRED` with `requires_user_decision`, structured audit (`policy_denied`, `authorization=stale`) and journal/memory evidence, and **no side effect**. AUTHORIZED cannot legally transition to WAITING_FOR_APPROVAL in current state machine; refusal uses a safe decision/recovery point. Legacy non-consequential AUTHORIZED tasks without durable context may continue only when current capability remains safely executable and no stricter consequential policy is detected (documented backward-compatible behavior).
- **Fresh authorization:** stale refusal does not execute the side effect; a fresh, explicitly authorized operation (new approval token bound to current capability/payload via supported workflow, e.g. `handle` with valid approval) can authorize the intended operation.
- **Real-path evidence:** `AJ/tests/test_f2_authorization_context.py` (12 tests) — unchanged context continuation; version/risk/approval-increase/forbidden/unavailable/payload-fingerprint changes refused; missing/malformed legacy consequential context fails closed; legacy non-consequential continuation documented; audit+journal evidence and no side effect on refusal; fresh approval permits intended operation via supported handle flow.
- **Remaining:** stale-policy handling for in-flight side effects, adapter-specific revalidation beyond spec metadata, and any future recovery/re-approve-on-same-task workflow remain **VERIFICATION REQUIRED** if introduced.
